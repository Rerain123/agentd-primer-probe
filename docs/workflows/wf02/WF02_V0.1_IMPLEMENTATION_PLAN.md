## 1. 硬性架构边界

### 1.1 只保留一套新的 WF-02

- `WF02V01BatchService` 是 WF-02 唯一业务编排入口。
- 主调用链固定为“大模型 → WF-02 MCP 工具 → `AgentDService` / `WF02V01BatchService`”；后端不嵌入第二套大模型 SDK。
- 旧 `WF02MultiplexPanel` 不作为新服务的依赖，也不保留第二套设计、组合、放宽、评分或报告逻辑。
- 旧 `/v1/wf02/multiplex` 如需兼容，只能映射到新服务的一次性运行入口，不能拥有独立算法。
- WF-06 在迁移节点完成后统一调用新 WF-02。
- 任务、科学计算、报告和 Agent 展示可以拆分为多个模块；模块拆分不代表存在多个工作流实现。

### 1.2 已完成 WF-01 阶段的非回归边界

- WF-02 只通过现有 WF-01 公共服务创建、推进、读取或创建子任务版本；内部保留的 `*_wf01_v02_*` 名称属于兼容接口名，不作为 WF-02 的业务规则来源。
- 每个靶标建立独立 WF-01 子任务；WF-02 不直接调用 Primer3 或 BLAST，也不允许模型自行生成候选序列。
- WF-02 不直接修改 WF-01 持久化的候选、阶段结果或 canonical report。
- 不修改 `src/agentd/wf01_v02*.py` 的科学计算行为。
- 不修改现有 WF-01 REST/MCP 字段含义、状态机、Schema、报告和附件语义。
- P6 由 WF-02 在第二阶段通过 `AgentDService` 服务网关执行，结果只写入 WF-02 的候选快照；P6 不回写 WF-01。
- WF-02 使用独立的 `wf02-v01-batches` 与 `wf02-v01-drafts` 状态目录、Schema、报告 ID、附件目录和版本谱系。
- 依赖方向只能是 `WF-02 → WF-01`；WF-01 不得导入 WF-02 模块。
- 每个影响运行代码的 WF-02 变更都必须运行 WF-01 回归门禁；失败时不得将对应节点标记为 `VERIFIED`。

## 2. 状态定义与更新规则

### 2.1 流程图状态

`流程状态` 原样保留 HTML 的证据结论，不随代码实现进度变化：

- `CONFIRMED`：来源资料已经明确。
- `PRODUCT`：产品层已经给出实现建议或交互定义。
- `CONFLICT`：来源资料存在冲突，需要登记最终选择。
- `PENDING`：关键判定尚未定义。

### 2.2 实现状态

- `NOT_STARTED`：尚未开始。
- `IN_PROGRESS`：正在实现，尚未形成完整验证证据。
- `IMPLEMENTED`：代码已完成，节点级测试或回归门禁尚未全部通过。
- `VERIFIED`：代码、节点验收、接口契约和 WF-01 非回归门禁全部通过。
- `BLOCKED`：存在外部数据、科学工具或未决规则阻塞。

### 2.3 节点完成定义

一个节点只有同时满足以下条件才可标记为 `VERIFIED`：

1. 节点行为和所有入边、出边与 HTML 一致。
2. 代码位置已写入节点台账。
3. 至少一个正常用例和一个适用的失败/边界用例通过。
4. 结构化 `workflow_trace` 能追溯到对应节点编号。
5. 涉及规则选择时已引用一个状态为 `ACCEPTED` 的 `WF02-D-*` 决策。
6. WF-01 回归门禁通过，且现有 WF-01 MCP/REST 契约没有变化。
7. 本文档的节点行和实施记录与代码处于同一次变更中。

禁止先把节点勾成完成、后补测试或实施记录。
